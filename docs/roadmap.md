## 2. 設計上の大きな決定

### 2-1. エンジンを「ルールの組み合わせ」に作り直す（最優先）
今の `computeLayout()` は、グリッド → サイズ → 重心 → 対比 を順番に処理する一本の関数。
30 を超える理論が互いに影響し合う（例：重さの場 × 面積の対比 × 方向の対比）と、この方式では破綻する。

**新しい形：コスト関数＋局所探索**
- 各理論を `Rule` モジュールにする。各ルールは配置の「良くなさ」を数値（コスト）で返す
- エンジンは、候補の配置（グリッド点・サイズ段階・反転など）を試し、**重み付きコストの合計が下がる手** を選ぶ
- 色・動き・描画のルールは、別の段（パイプライン）として順に適用する
- ルールごとに ON/OFF と重みを持ち、テストで個別に検証できる
- 理論が増えても、エンジン本体を変えずにルールを足すだけで済む。Godot へ移植するときも、ルール単位で移せる

### 2-2. 「師匠プリセット」で選ばせる
30 個のスイッチをユーザーに見せるのは無理がある。理論を師匠ごとにまとめたプリセットにする：

| プリセット | 主なルール |
| --- | --- |
| カンディンスキー | 重さの場、線の温度、角度と色、共感覚の音 |
| イッテン | 7 つの対比、面積の対比、6 形 6 色 |
| アルバース | 透明の錯覚、振動する境界、オマージュ、折り、経済性 |
| モホリ＝ナジ | 光と影、素材、万華鏡 |
| シュレンマー | 三つ組、スコア、形の文法 |
| ブロイヤー／グロピウス | 骨格と浮かぶ面、規格化と多様性、収納 |

詳細設定では個別の ON/OFF と重みも触れるようにする。

### 2-3. 「なぜこう動いたか」を見せる
理論がアプリの肝なので、図形が動いた理由（例：「重さの場：右下が重すぎるため上へ」）を短く表示する理論ガイドを用意する。学びのアプリとしての価値にもなる。

### 2-4. 描画を WebGL にするかの判断（フェーズ 4 の前）
光と影・素材・透明表現（N7, N10, N22）は Canvas 2D でも作れるが、品質と速度の限界がある。フェーズ 4 の開始前に、PixiJS（WebGL）へ移すかを判断する。

## 4. フェーズ 0.5 の補足：スマホでの確認方法
クラウドで作業している間、変更をスマホで試せる場所が必要。
- 案 A：GitHub Pages に Web 版を自動公開する（push のたびに更新）。リポジトリが非公開の場合は GitHub の有料プランが必要
- 案 B：Vercel や Netlify など外部のホスティングに接続する（非公開リポジトリでも無料枠あり。ユーザー側でアカウント連携が必要）
- 案 C：手元の PC で `npm run dev` を起動し、同じ Wi-Fi のスマホから開く（ローカル作業時）

## 5. 各フェーズの完了条件
- 追加したルールごとに単体テストがある（コストが意図した方向に効くこと）
- スマホ幅のブラウザで操作を確認し、スクリーンショットを残す
- `bauhaus-theory.md` の該当項目に「実装済み」と書き、実装とのずれを記録する
