## 2. 設計上の大きな決定

### 2-1. エンジンを「ルールの組み合わせ」に作り直す（最優先）
今の `computeLayout()` は、グリッド → サイズ → 重心 → 対比 を順番に処理する一本の関数。
30 を超える理論が互いに影響し合う（例：重さの場 × 面積の対比 × 方向の対比）と、この方式では破綻する。

**新しい形：コスト関数＋局所探索**
- 各理論を `Rule` モジュールにする。各ルールは配置の「良くなさ」を数値（コスト）で返す
- エンジンは、候補の配置（グリッド点・サイズ段階・反転など）を試し、**重み付きコストの合計が下がる手** を選ぶ
- 色・動き・描画のルールは、別の段（パイプライン）として順に適用する
- ルールごとに ON/OFF と重みを持ち、テストで個別に検証できる
- 理論が増えても、エンジン本体を変えずにルールを足すだけで済む。Godot へ移植するときも、ルール単位で移せる

### 2-2. 「師匠プリセット」で選ばせる
30 個のスイッチをユーザーに見せるのは無理がある。理論を師匠ごとにまとめたプリセットにする：

| プリセット | 主なルール |
| --- | --- |
| カンディンスキー | 重さの場、線の温度、角度と色、共感覚の音 |
| イッテン | 7 つの対比、面積の対比、6 形 6 色 |
| アルバース | 透明の錯覚、振動する境界、オマージュ、折り、経済性 |
| モホリ＝ナジ | 光と影、素材、万華鏡 |
| シュレンマー | 三つ組、スコア、形の文法 |
| ブロイヤー／グロピウス | 骨格と浮かぶ面、規格化と多様性、収納 |

詳細設定では個別の ON/OFF と重みも触れるようにする。

### 2-3. 「なぜこう動いたか」を見せる
理論がアプリの肝なので、図形が動いた理由（例：「重さの場：右下が重すぎるため上へ」）を短く表示する理論ガイドを用意する。学びのアプリとしての価値にもなる。

### 2-4. 描画を WebGL にするかの判断（フェーズ 4 の前）
光と影・素材・透明表現（N7, N10, N22）は Canvas 2D でも作れるが、品質と速度の限界がある。フェーズ 4 の開始前に、PixiJS（WebGL）へ移すかを判断する。

### 2-5. プリセットの自動切り替え（「指揮者」）
プリセットを自動で切り替える仕組みを **指揮者（Conductor）** と呼ぶ。切り替えは 5 つのルール（A〜E）の組み合わせで決める。

#### ルール A：バウハウスのカリキュラム（物語の骨格）
グロピウスのカリキュラム図（1922–23）は同心円で、外側から中心へ進む：
**予備課程（外周）→ 素材別の工房（中間）→ 建築 Bau（中心）**。
これを、プリセットが巡る順路にする。

| 段 | カリキュラム | プリセット | 画面の性格 |
| --- | --- | --- | --- |
| 1 | 予備課程 | イッテン → アルバース | 対比・素材・経済性の練習。要素が整理される。**モノトーンで始める**（予備課程の中心は明暗対比だったため） |
| 2 | 形態論 | カンディンスキー → クレー | 重さの場、線の温度、緊張と運動 |
| 3 | 工房（木・金属・ガラス・織物…） | ブロイヤー → モホリ＝ナジ（＋ヴァーゲンフェルト、ブラント） | 骨格と面、素材、光と影 |
| 4 | 舞台 | シュレンマー | 三つ組、スコア、形が動きを決める |
| 5 | 建築（中心） | グロピウス | 規格化、複合体、収納。すべてが一つの「建物」にまとまる |

中心の「建築」で全図形が収納（N17）されたら、外周の予備課程へ戻って展開する。これが一巡する周期になる。

#### ルール B：画面の診断（状況に応じた処方）
各プリセットに「いまの画面に、この師匠がどれだけ必要か」を表す **適合度** を持たせ、画面の特徴量から計算する。

| 画面の状態（特徴量） | 呼ばれる師匠 |
| --- | --- |
| 重心が大きく偏っている、上下の緊張がない | カンディンスキー |
| 色数が多いのに対比が弱い、色の面積がばらついている | イッテン |
| 図形の重なりが多い、□が多い、要素が多すぎる | アルバース |
| 直線が多い | ブロイヤー、クレー |
| 図形どうしのすき間がない（密集） | ブロイヤー（浮かぶ面） |
| 同じ形・同じサイズばかり（単調） | グロピウス（規格と変化） |
| Auto Flow 中で動きが大きい | シュレンマー、モホリ＝ナジ |
| 3 の倍数の要素、三角形が多い | シュレンマー |

ルール A の順路を基本にし、ある師匠の適合度が突出したときだけ、順路を飛ばしてその師匠を呼ぶ。

#### ルール C：飽和したら対極へ（イッテンの対比の原理）
いまのプリセットのコストが下げ止まった（構図が「解けた」）状態が一定時間続いたら、次へ進む。
次の師匠は、ルール A の順路の次か、いまの師匠と **最も対照的な師匠** を選ぶ（例：静的なアルバース → 動的なカンディンスキー、密なグロピウスの収納 → 疎なブロイヤー）。対比を予備課程の中心原理にしたイッテンの考え方を、プリセットの流れそのものに当てはめる。

#### ルール D：ユーザーが飽きたころに切り替える（最優先の引き金）
バウハウスの理論ではなく、美の心理学が根拠。バーラインの覚醒理論（1971）では、新しさや複雑さに対する心地よさは逆 U 字（ヴント曲線）を描く。同じ刺激に慣れる（馴化）と心地よさが下がるので、そこで新しい秩序を見せる。

**飽きのサイン（端末内の操作から推定）**
| サイン | 測り方 |
| --- | --- |
| 操作が減ってきた | 直近の操作頻度が、そのユーザー自身の平均より下がった |
| 同じことの繰り返し | 同じツール・同じ操作が続く、元に戻す・消去を繰り返す |
| 目新しさを探している | カオス ⇄ 秩序のトグルや万華鏡のオンオフを何度も押す |
| 画面が止まっている | 構図がほぼ変わらず、Auto Flow もオフのまま時間が経つ |
| いったん離れて戻ってきた | アプリが背面から戻った（新しい師匠で迎える） |

**夢中のサイン（このときは切り替えない）**
- 描いている、ドラッグしている、加工パネルを開いている
- 2 本指で拡大して細部を見ている
- 操作がなくても、Auto Flow や万華鏡を眺めている（「見入っている」）。眺めている時間が長くなったら、同じ師匠のまま動きや色調だけを変える小さな変化から始める

**飽き度スコア**：上のサインを重み付けして 0〜1 の「飽き度」を出す。しきい値を超えたら次の師匠へ進む。夢中のサインがあるときは 0 に戻す。

**まだ見ていない師匠を優先**：そのセッションで出ていない師匠を選びやすくし、新しさを保つ。

**好みの学習（任意）**：師匠ごとに「飽きるまでの時間」を端末内に記録し、長く楽しんだ師匠を少しだけ選ばれやすくする。データは端末の外に出さない（プライバシーポリシーにもそう書く）。

#### ルール E：形態の種類と数（どの師匠を呼ぶかの主な基準）
画面にある形の **種類の構成比** と **数** から、師匠ごとの適合度を計算する。各師匠が深く結びついた形をそのまま使うので、理論とのつながりが最も分かりやすい。

**形の種類 → 師匠（親和度の表）**
| 多い形 | 呼ばれる師匠 | 理由 |
| --- | --- | --- |
| △ 三角形 | カンディンスキー | 鋭角＝黄＝緊張、角度と色の理論 |
| □ 正方形 | アルバース、グロピウス | 正方形へのオマージュ、規格化された単位 |
| ○ 円 | モホリ＝ナジ | 回転、光、空間の万華鏡 |
| ─ 直線 | ブロイヤー、クレー | 骨格と浮かぶ面、散歩する線 |
| △□○ がほぼ同数 | シュレンマー（＋ケラー） | 三つ組、三原形＝三原色 |
| 台形・楕円・球面三角形 | イッテン | 6 形 6 色の対応 |

**形の数 → 師匠（区切りはフィボナッチ数）**
| 数 | 段階 | 呼ばれる師匠 |
| --- | --- | --- |
| 1〜2 | 習作 | イッテン、アルバース（1 つの対比をじっくり見る） |
| 3 | 三つ組 | シュレンマー |
| 4〜7 | 構成 | カンディンスキー、クレー |
| 8〜12 | 構造 | ブロイヤー、モホリ＝ナジ |
| 13〜20 | 規格 | グロピウス（規格化と変化） |
| 21〜 | 建築 | グロピウス（収納）、アルバース（経済性で間引く） |

**種類の偏り（多様性）**
- 1 種類に偏っている → グロピウス（同じ規格から変化を生む）、または偏った形の師匠をさらに強める
- 種類がばらばら → イッテン（対比で整理する）

**適合度の計算**
`適合度 = Σ（形の構成比 × 親和度） ＋ 数の段階の加点 ＋ 多様性の加点`
表の数値は 🛠（アプリのための設計）で、実機で調整する。

**「いつ」の引き金にもなる**：新しい種類の形が初めて置かれた、または数がフィボナッチの区切りをまたいだら、師匠を見直す。たとえば初めて直線を引くとブロイヤーが現れ、3 つ目の図形でシュレンマーが現れる。ユーザーの操作に画面が「応える」感覚が生まれる。ただし飽き度（ルール D）が低く夢中のサインがあるときは、切り替えではなく理論ガイドで「次はブロイヤーが待っています」と予告するだけにする。

#### 5 つのルールの関係
- **いつ** 切り替えるか：ルール D（飽き）が主な引き金。ルール E（形の種類・数の節目）と ルール C（構図が解けた）が補助
- **どこへ** 切り替えるか：ルール E（形の種類と数）の適合度が主な基準。同点ならルール A（カリキュラムの順路）の順番、ルール B（画面の診断）で処方が必要なら補正し、ルール C（対極）で意外性を加える

#### 切り替えの見せ方
- **一瞬で切り替えない**：ルールの重みを数秒かけて補間し、構図がゆっくり別の秩序へ移る。移り変わりそのものを見せ場にする
- **ちらつき防止**：一度切り替えたら最低滞在時間を設け、適合度にはしきい値の幅（ヒステリシス）を持たせる
- **理論ガイドで告知**：「アルバースへ：色の重なりが増えたため」のように理由を表示する
- **ユーザーの操作が優先**：自動 ON/OFF、いまの師匠に固定、順路の速さ（ゆっくり／ふつう／速い）を選べる。ユーザーが描いている間は切り替えを控える

#### エンジン設計への影響（フェーズ 1 で対応）
- ルールの重みを ON/OFF ではなく **連続値** で持つ（補間できるように）
- 各ルールのコストを毎回記録する（飽和の検出に使う）
- 画面の特徴量（重心のずれ、色数、重なり率、密度、形の種類の偏りなど）を計算する関数を用意する
- 操作の記録（時刻・種類）を残す仕組みをストアに用意する（飽き度の計算に使う。端末内のみ）

### 2-6. 色調モード：カラー／モノトーン／モノトーン＋1 色（N25）
色を外すと、バランスの決まり方そのものが変わる。

**カラーとの違い**
| | カラー | モノトーン |
| --- | --- | --- |
| 重さを決めるもの | 明るさ＋色相（寒色ほど重い）＋面積 | **明るさと面積だけ** |
| 形と色の対応（△黄など） | 効く | 効かない → 形そのものの対比（大小・向き・位置）が主役になる |
| イッテンの対比 | 7 種類 | **明暗対比だけ**（予備課程の出発点。最も基本的な対比） |
| 面積の対比 | 色ごとの比率 | 明るさの段階ごとの比率 |
| 重なり | 色が混ざる（乗算） | 濃淡が重なる（写真のフォトグラムのような表現） |

**ルール**
- 明るさは **7 段階**（イッテンの色彩球は 7 つの明度段階で構成されている）
- カラーから切り替えるときは、元の色の見かけの明るさを保つ（黄→明るい灰、青→暗い灰）。このため、カンディンスキーの重さの順（青＞赤＞黄）は明暗としてそのまま残る
- 画面全体で明暗の段階がまんべんなく使われるようにする（同じ灰ばかりなら段階を散らす）
- 背景が白なら黒い図形ほど重く、背景が黒なら白い図形ほど目立つ。重さの計算は「背景との明暗差」で行う

**モノトーン＋1 色**：バウハウスの印刷物（黒と赤）にならい、白黒の中で 1 つだけ色を残す。残す 1 つは、最も重要な図形（直前に触った図形、または最大の図形）にする。

**指揮者との関係**
- カリキュラムの最初（予備課程）はモノトーンで始まり、形態論の段で色が入る
- 色数が多すぎて飽きのサインが出たら、いったんモノトーンへ「引き算」する（アルバースの経済性）
- ユーザーはいつでも手動でカラー／モノトーン／＋1 色を選べる

## 4. フェーズ 0.5 の補足：スマホでの確認方法
クラウドで作業している間、変更をスマホで試せる場所が必要。
- 案 A：GitHub Pages に Web 版を自動公開する（push のたびに更新）。リポジトリが非公開の場合は GitHub の有料プランが必要
- 案 B：Vercel や Netlify など外部のホスティングに接続する（非公開リポジトリでも無料枠あり。ユーザー側でアカウント連携が必要）
- 案 C：手元の PC で `npm run dev` を起動し、同じ Wi-Fi のスマホから開く（ローカル作業時）

## 5. 各フェーズの完了条件
- 追加したルールごとに単体テストがある（コストが意図した方向に効くこと）

- `bauhaus-theory.md` の該当項目に「実装済み」と書き、実装とのずれを記録する
